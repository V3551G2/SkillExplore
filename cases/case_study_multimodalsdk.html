1 任务背景与输入

用户提供了一个运行在华为云 CodeArts 上的 PR 流水线链接，要求将其转换为 GitCode Actions YAML 格式，并推送到指定测试组织验证。输入参数包括：

参数值
流水线 URLhttps://devcloud.cn-north-4.huaweicloud.com/cicd/project/609138a9.../pipeline/detail/44a32df0...
测试组织https://gitcode.com/ComputingActionTest
GitCode Token*********
CodeArts Cookie（包含 session、cftk 等完整登录态）
关键前置条件： CodeArts REST API 需要带 cftk CSRF token 和完整 cookie 才能返回 JSON；否则会返回 SPA HTML 页面。cftk 从 cookie 字段 devclouddevuibjtcftk 提取，region 从 *_cfProjectName 提取。

2.3 语法问题反馈

👤 用户

🤖 助手

确认问题：stage name 中的 & 是 YAML 特殊字符/不被 GitCode 解析器接受。立即将 CodeCheck&Build&Test 改为 CodeCheck_Build_Test，在 master 和 master_test 分支上分别提交并 push。

Phase 1 抓取流水线配置

使用 PowerShell + curl.exe（规避 Invoke-RestMethod 的 TLS/证书问题），构造包含所有必要 header 的请求：

# 从 cookie 提取认证信息
$cftk = [regex]::Match($cookies, 'devclouddevuibjtcftk=([^;]+)').Groups[1].Value
$region = "cn-north-4"
$base = "https://devcloud.${region}.huaweicloud.com"

# 获取流水线定义
$pipelineJson = & curl.exe -sk `
  -H "Cookie: $cookies" `
  -H "X-Requested-With: XMLHttpRequest" `
  -H "cftk: $cftk" `
  -H "Accept: application/json" `
  -H "language: zh-cn" `
  -H "projectname: $region" `
  "$base/cicd/v5/internal/$projectId/pipelines/$pipelineId"

# definition 是 JSON 字符串，需要二次解析
$definition = $pipeline.definition | ConvertFrom-Json

获取到的关键信息

  • 流水线名称: PR-pipeline_MultimodalSDK
  • 源仓库: https://gitcode.com/Ascend/MultimodalSDK.git (默认分支: master)
  • 敏感变量: Atlas_password (secret), presmoke_image, TARGET_BRANCH, REMOTE_URL

之后对每个 enabled 的 CloudBuild step，提取 jobId 并调用 GET /codeci/v1/job/<job_id>/config?get_all_params=true 获取详细配置，共 9 个 job 配置文件保存为 JSON。

4.2 统一资源池（Unified Pool）模式识别

Build_arm、UT_cpp、PreSmoke 三个 job 均采用 CodeArts 统一资源池模式，特征如下：

  • Step 顺序：执行shell命令 (20017) → 下载文件管理的文件 (20061) → 使用SWR公共镜像 (20028)
  • SWR 镜像：swr.cn-southwest-2.myhuaweicloud.com/modelfoundry/karmada:latest（karmada 调度器）
  • SWR 命令：/workspace/workflowtool/entrypoint.sh
  • Job 参数包含 CP_docker_image 和 CP_runs_on
转换规则：
  1. 丢弃 step 2（下载 kubeconfig）— CodeArts 调度基础设施
  2. 丢弃 step 3（karmada 容器）— 跨集群调度无需在 GitCode 中实现
  3. 从 step 1 的 heredoc 中提取真实脚本（cat > shell.sh <<- 'EOF' ... EOF）
  4. 容器镜像使用 CP_docker_image（非 karmada wrapper）：swr.cn-north-4.myhuaweicloud.com/ascend-mindx/mindx_arm:SDK_20260112_1
  5. runs-on 映射：arm64-cpu-*-mem-* → arm64；arm64-npu-* → arm64 + npu 标签

例如 Build_arm 的 heredoc 提取后得到构建脚本，核心逻辑包括：clone dev repo → fetch PR ref → merge → wget CI tar（被消除）→ cd ci/MultimodalSDK && bash prepare_dependency.sh → obsutil cp obs://mindcluster/opensource.tar.gz → cd build_script && bash build_merge.sh → 收集 .run 产物。

4.3 CI 仓库脚本迁移（Category A vs B）

区分两类脚本是转换正确的关键：

分类说明处理方式
Category A（目标仓库内）clone dev repo 后 cd ${servicename_1}/build_script 下的脚本，如 build_merge.sh、run_presmoke.sh保留原路径，不移动
Category B（外部 CI 仓库）从 MindCluster-CI 或 MindSDK-CI clone/wget 的脚本，如 codesca.py、anti_poison.py、prepare_dependency.sh迁移到 scripts/，消除 CI clone 逻辑

本案例涉及两个 CI 仓库：

  • Ascend/MindCluster-CI（被 Clone_Private_Static 和 SCA/Antipoison/pre-commit job 引用）→ 含 codesca.py、anti_poison.py、precommit_check.sh、codecheck.py
  • Ascend/MindSDK-CI（被 Clone_Private_Repository 和 Build/UT/PreSmoke job 引用）→ 含 MultimodalSDK/prepare_dependency.sh
实际问题：尝试通过 curl 匿名下载这些脚本时，返回的是登录 HTML 页面（两个 CI 仓库均为私有）。因此全部创建了空占位文件，在 summary 中提示用户手动填充。

入口工作流关键设计

# PR-pipeline_full.yml 核心结构
name: PR-pipeline_full
on:
  pull_request_target:
    branches: [master]
    types: [open, update, reopen, merge]
  pull_request_comment:
    types: [created]
    branches: ['*']
    comments: ['^(?:\/)?compile*']
  workflow_dispatch:

env:  # 使用 env 而非 inputs，避免 PR 触发时 inputs 未被填充
  BUILD_SKIP: "no"
  REPO_NAME: ${{ atomgit.event.repository.name }}
  PR_ID: ${{ atomgit.event.pull_request.number }}
  TARGET_BRANCH: ${{ atomgit.event.pull_request.base.ref }}
  REMOTE_URL: ${{ atomgit.repositoryurl }}

stages:
  stage_0:
    name: CodeCheck  # & → _ （修复后）
    jobs:
      Only_doc_commit_check: ...
  stage_1:
    name: CodeCheck_Build_Test  # 原 CodeCheck&Build&Test，& 不符合语法
    jobs:
      SCA: ...
      Antipoison: ...
      pre_commit: ...
      SAST: ...
      Build_arm: { uses: .gitcode/workflows/.build_job.yml, with: { IMAGE_FLAG: "mindx_arm:SDK_20260112_1", runs_on_arch: "arm64" } }
      UT_cpp: { uses: .gitcode/workflows/.ut_cpp.yml, ... }
      PreSmoke: { uses: .gitcode/workflows/.presmoke.yml, ... }

关键转换点

1. env: 而非 inputs:（入口工作流）

PR 触发时 inputs 不会被 atomgit context 填充，必须用 env: 定义系统变量，通过 ${{ env.PR_ID }} 引用。子工作流可以正常用 inputs（因为 uses 显式传参）。

2. 容器镜像必须是字面量（入口工作流）

入口工作流中 container.image 必须是硬编码字符串，不能是 ${{ env.xxx }}，因为容器解析在 env 评估之前完成。

3. git merge committer identity

所有 clone+merge 步骤在 git merge 前必须配置身份，否则容器内 git 报错：

git config --global user.name AtlasAccount
git config --global user.email AtlasAccount@noreply.gitcode.com
git merge --no-edit pr_${{ inputs.PR_ID }}

4. CWD 不跨 step 持久化

GitCode 每个 run: block 都从 ${ATOMGIT_WORKSPACE} 重新开始。将单一 heredoc 拆分为多个步骤时，每步开头必须显式 cd 到正确绝对路径。为安全起见，本案例将 build 步骤合并为较少的大块。

9 经验教训

  1. CodeArts API 认证必须齐全：缺少 X-Requested-With: XMLHttpRequest 或 cftk header 会返回 SPA HTML 而非 JSON。
  2. PowerShell 调用 curl.exe 时 body 编码坑：ConvertTo-Json | Out-File 默认带 BOM，导致 API 返回 400 "Request body parsing error"。必须用 [System.IO.File]::WriteAllText(path, json, [System.Text.Encoding]::ASCII)。
  3. GitCode Fork API 参数名：创建 fork 时 body 内的组织字段为 "organization"（不是 "org"）；创建 PR 时分支字段为 "head"/"base"（不是 "source_branch"/"target_branch"）。
  4. stage name 不能含特殊字符：&、?、* 等在 GitCode stage name 中会导致解析错误。命名使用 _ 连接，如 CodeCheck_Build_Test。
  5. 入口工作流用 env: 而非 inputs:：inputs 在 PR 触发时不会从 atomgit context 填充，导致 "Input required and not supplied"。系统变量一律放 env:。
  6. demo_mindx 镜像需要 git upgrade：老版镜像 huawei-ascend/demo_mindx:mindxdl_20230912_1 自带 git 2.17，低于 checkout action 要求的 2.18，必须在 checkout 前添加 PPA git 升级 step。
  7. 私有 CI 仓库无法匿名下载脚本：需要预判这种情况，创建 placeholder 文件并在 summary 中明确提示用户手动填充，不能假设 CI 仓库公开。
  8. Category A/B 脚本区分：不能看到 bash script/xxx.sh 就认定是 CI 脚本。必须判断该路径是在 clone dev repo 后（Category A，保留）还是在 clone CI repo 后（Category B，迁移）。错误迁移会导致路径不匹配的运行时错误。
  9. PreSmoke 需要 npu runs-on 标签：当 CP_runs_on 包含 npu 时（如 arm64-npu-1-cpu-64-mem-128G），runs-on 需加入 npu 标签：[dedicate-hosted, arm64, npu, large]。
  10. 测试 PR 需非 .md 文件才能触发完整流水线：md_check job 会在 PR 仅修改 .md 文件时将 build_skip 设为 "yes"，导致下游所有 job 被跳过。验证完整流水线时需提交非 .md 文件。
