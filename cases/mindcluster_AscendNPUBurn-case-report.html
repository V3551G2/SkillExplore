01处理流程：四个阶段

技能规定的标准动线是「抓取 → 转换 → 产物校验 → 闭环验证」，前三个阶段在本地完成，第四个阶段在测试组织里真跑真修。

阶段一 · 通过 CodeArts REST API 抓取配置

从流水线 URL 解析出 project_id=609138a9…、pipeline_id=1b4df40d…、region 与 cftk，再调内部接口拿到 definition（stage/job/step 的 JSON）和 variables。关键动作是在三个层级过滤掉禁用项：

  • 作业的 strategy.select_strategy == "never" → 整作业跳过；
  • 流水线 step enable: false → 跳过该 step；
  • 作业配置 step enable == false → 跳过该 step。

只对启用的 official_devcloud_cloudBuild 步骤去拉 /codeci/v1/job/<job_id>/config，避免对废弃作业做无用功。随后识别出统一资源池特征——执行shell(20017) → 下载kubeconfig(20061) → SWR karmada(20028) 三连，其中后两步是 CodeArts 基础设施，直接丢弃，从 20017 的 heredoc 里抽出真正的脚本，以 CP_docker_image 作为容器镜像，CP_runs_on 映射架构（amd64→x64，arm64*→arm64）。

阶段二 · 作业分类与 YAML 转换

把 9 个启用作业逐一归类，决定每种的转换范式。这是整个转换中决策最密集的一步：

转换中坚持的几条硬规则：PR 流水线只挂 pull_request_comment（评论 ^(?:\/)?compile*）+ workflow_dispatch，不加 pull_request_target；stage 名用 _ 不能用 &；镜像名写成 env: 字面量；子工作流调用只传 required:true 的输入（IMAGE_FLAG、runs_on_arch），由子工作流自己取 atomgit 默认值——重复传 REMOTE_URL/pr_id/TARGET_BRANCH 会触发 "bad substitution"。

阶段三 · 产物落盘与静态校验

在 .gitcode/workflows/ 下生成 4 个 YAML（入口 + 3 个子工作流）和 scripts/（anti_poison.py 及真实的华为 apig_sdk/，用带 PRIVATE-TOKEN 的鉴权下载拿到真实内容，而非占位空文件）。同时放 .gitattributes 强制 *.yml/*.sh/*.py 走 LF——Windows 上 core.autocrlf=true 曾把脚本转成 CRLF，会导致容器里 bash\r 报错，提交后用 git cat-file 校验 blob 内无 CR。

阶段四 · 闭环验证（核心阶段）

把产物推到 fork ComputingActionTest/MindCluster-AscendNPUBurn 的 master，建测试 PR #1，用户开启「PR 预合并 / Actions」后，用 v5 接口发评论 /compile 触发；通过 v8（api.gitcode.com，注意不是 gitcode.com）轮询 runs/jobs，download_log 拿到的是 302→ZIP 的逐步骤 .log。每轮失败都下日志、定位根因、把 YAML 修复推到目标分支 master（评论触发器读的是目标分支上的 YAML），脚本修复则在 PR 分支生效。整个修复设了上限：最多 3 次 YAML 修复，超出后剩余失败归为 needs_human / known_limit。

03遇到的问题与修复

下面按"真实代码缺陷 → 环境/平台问题 → 自我纠错"分组。每个问题给出错误现象、根因和最终修法——包括一次走了弯路又退回正轨的过程。

P1

checkout 报 git 版本过低

YAML 修复
现象
要求的最低git版本是 2.18, 当前git ('/usr/bin/git') 版本为 2.17.1
根因
demo_mindx:mindxdl_20230912_1 与 mindx_x86:mindxdl_go1207_20251203 基于 Ubuntu bionic，自带 git 2.17.1，低于 checkout 动作要求的 2.18。
修复
在这些已知旧 git 镜像的 checkout 之前加 git 升级步骤（apt → PPA → 安装）。Detect、Antipoison、SAST 三个作业需要。
- name: git upgrade
  run: |
    apt-get update
    apt-get install -y software-properties-common
    add-apt-repository -y ppa:git-core/ppa
    apt-get update
    apt-get install -y git
    git --version
P2

把 git 升级误加到 mindspore 镜像（一次弯路）

已纠正
现象
pre_commit 报 E: Unable to locate package software-properties-common（exit 100）。
根因
fix#1 给 mindspore_python3.11:v0.1 也加了升级步骤，但该镜像是 Debian trixie，没有 PPA 支持；而它自带 git 2.47.3 根本不需要升级。fix#2 写的"portable 版本判断块"只是在掩盖这个自找的错误。
修复
对照 FAQ #7 的镜像清单，直接删除 pre_commit 的 git 升级步骤。这是用户点名"checkout 插件问题有 faq 吧"后回到 FAQ 才发现的——FAQ 早已明确 mindspore 镜像不应加该步骤。教训：先查 FAQ，按镜像条件化加步骤，不要用兜底逻辑去救一个本不该存在的步骤。
P3

pre-commit 的 gitleaks 钩子找不到可执行文件

YAML 修复
现象
Executable './gitleaks' not found  (hook id: gitleaks-offline-scan, exit 1)
根因
钩子在仓库根目录执行 ./gitleaks，但最初把二进制装到了 /usr/local/bin。
修复
把二进制下到工作区根目录并赋可执行权限：
- name: gitleaks install
  run: |
    wget -q --no-host-directories -c --no-check-certificate \
      https://pytorch-package.obs.cn-north-4.myhuaweicloud.com/pta-codecheck/gitleaks
    chmod +x gitleaks
P4

Detect 因拉 GPG key 超时而失败

瞬时/重试
现象
git 升级步骤里 add-apt-repository 报 Error: retrieving gpg key timed out，Detect 失败导致整轮 stage_1 没启动。
根因
keyserver 网络抖动——完全相同的步骤在前几轮都成功，属偶发。
处理
重新发 /compile，下一轮 gpg key 拉取成功，Detect COMPLETED。未改代码。若反复出现可考虑给 add-apt-repository 加重试/多 keyserver 兜底，但单次抖动不值得动 YAML。
P5

专用 runner 长时间停在 QUEUED

资源调度
现象
run #6 中 Detect status=QUEUED / start_time=null 持续近 5 分钟，页面点重试后才分配到 runner。
根因
[dedicate-hosted, x64, 2xlarge] 专用宿主机调度延迟，非代码/YAML 问题。
处理
通过 start_time 是否为空区分"作业没开始"与"作业执行失败"，避免误判为转换缺陷；用户在页面重试解决。
P6

SCA 返回 repoUrl is null

平台配置
现象
响应状态码: 200
{"code":41003,"message":"repoUrl is null",

P7

PreSmoke 与 Build_arm 并行导致产物 404

真实缺陷 · 待落地
现象
JOB_smoke 在 03:17:15 wget artifacts_aarch64.zip 返回 404；而 arm 编译在 03:19:24 才把同名产物上传到 OBS。
根因
PreSmoke 与 Build_arm 同处 stage_1，同 stage 内作业默认并行，PreSmoke 没等产物就位就起跑。产物本身构建/上传都成功（OBS 报告 0.16s 上传成功），纯粹是时序竞态。
修复方案
把 PreSmoke 拆到独立的 stage_2（name Test），利用"stage 间串行"保证它在 Build_arm 之后执行。用户喊停前尚未推送，作为明确待办。
# 修复前：PreSmoke 与 Build_arm 同在 stage_1，并行抢跑
stages:
  stage_1:
    jobs:
      Build_arm: { uses: .build_job.yml, ... }
      PreSmoke: { uses: .presmoke.yml, ... }   # ← 同时起跑，404

# 修复后：PreSmoke 移到独立 stage_2，天然等 stage_1 全完成
stages:
  stage_1: { jobs: { SCA, pre_commit, Antipoison, SAST, Build_x86, Build_arm, UT_Python } }
  stage_2:
    name: Test
    jobs:
      PreSmoke:
        if: ${{ jobs.Detect_file_changes.outputs.need_build == 'yes' }}
        uses: .gitcode/workflows/.presmoke.yml
        ...

仍需注意

PreSmoke 本身要在 arm64 + NPU 加速卡的 runner 上跑（装 ascend_npu_burn wheel、source cann-A2、跑 run_st.sh），属于环境级 known-limit。stage_2 修复解决的是"抢跑 404"，让它在有卡的环境里能真正走到 smoke 逻辑。
P8

轮询脚本与 Windows 路径的自我纠错

工具链
  • v8 列表接口字段是 workflow_runs 不是 runs，第一次后台监控因此误报"无新 run"——改为正确字段后正常。
  • 状态终态是大写 FAILED/COMPLETED，监控脚本的 case 没匹配大写，漏掉了结束信号——补齐大小写匹配。
  • Windows Git Bash 下 /tmp/... 与 /d/... 在 curl 与 Node 间解析不一致，Node 找不到模块；改为 curl 直接管道给 Node stdin，并用 D:/ActionTest/.yamllint 风格的 Windows 绝对路径。
  • CRLF：靠 .gitattributes + git cat-file -p HEAD:<path> | grep -c $'\r' 验证 blob 干净（应为 0）。

04可复用经验与待办

建议补入技能/FAQ 的经验

  • git 升级必须按镜像条件化，严格照 FAQ #7 的清单加。mindspore 等较新镜像自带合格 git，加了反而在 Debian trixie 上因 software-properties-common 缺失而失败。
  • gitleaks 要装在工作区根目录：openlibing-pre-commit-action 的钩子执行 ./gitleaks，不是从 PATH 找。
  • 下载产物的后续作业必须排在独立 stage（PreSmoke → stage_2），因为同 stage 并行会抢跑。这是一条通用的"构建→部署"顺序规则。
  • 无 secret 干跑的判读标准：obs-upload 403、SCA/Antipoison 401 且编译本身成功 = 接线正确；PreSmoke 的 404 是缺产物的级联，不算独立缺陷。
  • 区分 QUEUED 与 FAILED：start_time 为空是资源调度问题，不要当成代码错误去修。
  • v8 API 的两个易错点：列表字段 workflow_runs、终态大写。

明确的遗留待办

  • PreSmoke stage_2 修复：方案已在 P7 给出，等你确认后推 master 再发一轮 /compile 验证（需要可用的 arm64+NPU runner）。
  • 8 个 secret 已配齐：OBS_AK/SK、SCAN_ACCESS_KEY/SECRET_KEY、四个 *_ANTI；ACCESS_QK 经验证为可选（SAST 用公开仓 TuBee/AI-Check，不需要）。
